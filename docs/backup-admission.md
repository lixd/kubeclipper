# Backup request admission

`POST /api/core.kubeclipper.io/v1/clusters/{name}/backups` returns HTTP 200 after the Backup admission record has been stored. This means accepted, not snapshot completed. The response includes the Backup name and `kubeclipper.io/operation-name` label; `X-Operation-Name` identifies the same operation. The controller publishes that operation from the recorded, validated plan and can resume publication after a server restart. A backup is usable only when `backupStatus.status` is `available` and the snapshot checksum and size are present.

For safe network retries, send an `Idempotency-Key` of 1–128 printable ASCII characters without spaces. Reuse it with the same backup name, preferred-node input and description. Within a Cluster UID, the same key and parameters return the existing Backup, including while the Cluster is busy. Changed parameters return HTTP 409. The idempotency record is retained with the Backup. If the Backup has been deleted but its Operation history remains, replay returns HTTP 410 and requires a new key instead of creating a new Backup against an old Operation identity. Independent requests without a key remain separate backups. The current kcctl has no backup-create subcommand; API callers must retain their key. `kcctl get backup -o yaml` exposes the stored association.

The first admitted Backup to reserve a Running Cluster changes it to BackingUp before its Operation is published. Another admitted backup waits while the Cluster is busy. The existing Operation V2 execution lock still serializes execution. The owner UID remains after completion: an old publisher or terminal projection cannot overwrite a newer backup or another action's state.

A storage timeout is not proof that a write failed. The API reads back the stable Backup name; the publisher reads back the stable Operation name and verifies its identity. If the outcome cannot be confirmed, an error remains visible and the caller can repeat the same keyed request. The controller recovers from a committed Backup, a committed Cluster reservation, or a committed Operation without creating a second operation. Real storage errors are returned to the controller's normal retry mechanism and logs.

Existing backups and scheduled-backup creation keep their existing lifecycle. This change addresses manual backup creation admission; it does not redesign cron scheduling, backup deletion or restore admission.
