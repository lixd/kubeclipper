# OCI 安装资源与全局镜像仓库

## 目标及配置职责

平台在部署时选择安装资源 OCI 仓库，默认 ghcr.io/kubeclipper/kubeclipper，显式 --package-registry 优先。Server、Agent、containerd、Kubernetes 二进制和 Chart 均从正式解析计划指定的资源位置获取。仓库失败时直接失败。

部署登记对应的全局镜像 Registry 并记录平台默认引用；协议、地址、路径、认证、CA、TLS 校验设置保留。已有同名资源一致时复用，不一致时显式报冲突，不删除重建，不偷偷更改用户配置。现有配置 API 返回默认 Registry 引用供 Web 和 CLI 共用；不能由前端根据名称或安装资源字符串推测。

## 下载脚本

脚本默认下载 GitHub 的 kcctl，--mirror cn 选择既定国内下载站。未知参数失败。删除 KC_REGION 和 KC_DOWNLOAD_URL，不写 shell 配置或 /etc/kc/kc.env，不把地区传给平台部署。

## 创建与执行

未传 imageRegistry 时服务端解析平台默认 Registry，显式传入 Registry 名称时使用该对象；解析后将明确引用保存在集群。引用不存在、地址非法或默认未配置时返回可操作错误。CLI 与 Web 遵循相同规则。仅有一个 Registry 不能成为自动选择理由。新建集群没有在线离线执行模式，也没有组件镜像上游回退。

所有本次安装涉及的平台组件使用集群选择的统一镜像来源，包括 kubeadm 管理镜像、pause、Calico、已启用附加组件。路径使用发布镜像的命名布局，覆盖 CoreDNS、Tigera Operator 等实际路径。用户工作负载不在替换范围。安装资源和 Chart 不受集群镜像选择改变。版本列表来自正式资源清单；切换镜像仓库不清空用户版本选择。发现缺失资源或版本架构不匹配时明确失败；未验证的状态不标为完整可用，清单存在不等同于成功拉取或建群。

升级与扩容固定使用集群保存的仓库，平台默认变化不能影响它。本版不实现仓库迁移：升级 API 只接收目标版本，旧仓库覆盖字段明确拒绝；普通集群编辑也拒绝更改或清空集群仓库引用。目标版本遵守已有版本升级约束并检查资源。平台 join、upgrade 的安装资源使用当前部署来源，内网流程不悄悄回到公网；必要的本地发布清单及认证参数继续保留。

## UI

创建页在版本旁保留一个“镜像仓库”必填选择，默认使用 API 提供的平台 Registry，选项和确认页展示仓库名称与地址。没有“使用组件默认来源”、在线离线开关、阿里云预置项或组件独立选择。问号仅为“用于拉取 Kubernetes、Calico 等组件的容器镜像。”。不展示安装包、Chart 或 Package Registry 说明。仓库加载失败可重试，已选对象消失时保留错误并要求重新选择，不静默换源。升级 UI 选择目标版本，现有镜像仓库只读展示，不提供切换。

Registry 管理填写名称和完整地址（含协议、可选端口路径），不让用户理解 host/repositoryPrefix；认证开启后才显示凭据字段，证书配置按需展开。地址只展示一次，长地址可查看完整内容，列表与选择器一致。

## CLI、清理及数据

create registry 使用 --address 接受完整地址；旧 host/scheme 地址输入方式退出，认证和证书参数继续支持。create cluster 的 --image-registry 参数为 Registry 名称且可省略，升级不提供 --image-registry 参数，始终沿用集群。删除 --offline、--online、--kc-image-repo-mirror、KC_IMAGE_REPO_MIRROR 及旧 env 文件读取。删除 HTTP 静态安装资源和安装包内镜像归档自动导入路径、两套版本列表、失效字段函数与测试，更新命令示例补全和文档。不新增兼容层。

旧测试 Registry 中 path-in-host 数据检查引用后按新结构一次性修正，无法明确转换的资源不静默改写。运行中的集群、操作、用户已有工作必须保留。

## 验证与交付

针对性单元、编译和 UI 检查覆盖两个来源流程、默认优先级、完整地址、错误和生命周期继承。sh-dev 使用包含本地未提交未跟踪源码的独立准确副本，记录校验清单。部署前检查活跃操作并备份回滚。仓库清单、完整拉取、实际建群分别报告，不用局部证据替代全部结果。不增强下载日志，不创建公共国内源，不做正式发布或未经授权的 Git 交付。

## 设计结论

采用“固定内容身份 → 本地原始内容存储 → 按需提取 → 安装消费”的流程。首期复用现有 Registry 配置及 go-containerregistry 元数据能力，以 containerd 独立 content store 作为原始内容存储的首选实现；补齐可取消的跨进程锁、响应体恢复和消费期间保护，不新建通用下载平台。

本设计明确四项契约：提取子集必须进入缓存身份；缓存返回路径后仍需保护；三类摘要必须分别校验；“按需提取”不能误写为“按文件下载”。以下作为实现和验收依据，不表示产品已经实现或通过验证。

## 1. 目标与边界

OCI 化后，Registry 是物料的发布和分发来源，本地缓存负责可靠获取和复用，安装目录负责实际运行。三者需要有清楚的职责和生命周期。

本设计希望解决：

- 同一压缩层中提取多个文件，不应反复读取远端完整压缩层。
- 网络断流后可以有限重试、恢复进度；不能将半包或损坏内容交给安装步骤。
- 缓存身份、并发、退出、清理都有明确规则，不留下无限增长的临时文件。
- deploy、Agent、sync 等路径遵循相同的完整性和错误处理原则，同时保留各自职责。

不改变已确认的仓库选择体验：创建集群使用一个全局镜像仓库；页面不增加 Package Registry、缓存位置、续传等内部选项。本设计不新增镜像源回退，不使用全局禁用 HTTP/2 掩盖问题，不自动提交、推送或部署。

## 3. 三类存储职责

| 存储 | 保存什么 | 生命周期与用途 |
| --- | --- | --- |
| 目标 Registry | 发布或 sync 后的 OCI 内容，包括所选发布范围内的包、Chart 和镜像 | 持久分发来源；离线环境应提前准备，不依赖某台机器碰巧命中过缓存 |
| KubeClipper 本地缓存 | 正在获取的数据、已验证原始内容、提取后的安装文件 | 可清理、可重建，用于可靠获取和复用 |
| 安装目录及 containerd 存储 | 已安装二进制、运行配置、运行时容器镜像 | 由安装和运行时生命周期管理，不属于 KubeClipper 缓存清理范围 |

本地缓存按机器、执行用户隔离。root 默认沿用 `/var/lib/kubeclipper/cache`；非 root 沿用 `os.UserCacheDir()/kubeclipper`；保留现有 `KUBECLIPPER_CACHE_DIR` 覆盖能力，不另增一套位置参数。

## 4. 目录与身份

```text
<cache-root>/
├── content/
│   ├── blobs/sha256/<digest>          # 完整校验并提交的原始内容
│   └── ingest/<transaction>/         # 未完成数据与恢复状态
├── packages/
│   └── <kind>/<name>/<version>/<os-arch>/<manifest-digest>/<selection-digest>/
│       ├── contents/                 # 提取文件
│       └── receipt.json              # 身份、文件摘要、完成状态
└── locks/                            # 下载、提取、读取和清理协调
```

已验证的平台 OCI manifest 原始字节也按 digest 存入 content store；重建时从中取得层 descriptor，再校验本地层及包清单。这样只有提取快照被清理时，无需重新请求 Registry。若计划仍需远端解析，或必要元数据、层已被清理，则不能承诺离线命中。

目录为逻辑方案，最终命名以选用的 content store 和现有调用接口为准。`receipt.json` 表示提取完成记录，不是 OCI manifest，也不是证明仓库当前可访问的健康状态。

提取缓存采用不可变快照，不在已发布目录上增量追加文件。`selection-digest` 是本次所需文件集合的规范化摘要：按文件名排序，包含内容名称、目标相对路径、media type、预期摘要及提取格式版本；集合顺序不同应得到相同身份。join 的 agent 子集与 deploy 子集可分别存放，但共享原始 blob。首期接受少量重复提取空间，避免可变 receipt 与正在使用的文件之间发生竞争，不实现子集查找优化。

原始 blob 按内容 digest 标识；组件名、版本和平台用于人类识别，manifest digest 用于区分同版本不同内容。恢复记录至少绑定预期 digest、大小和来源身份；不保存口令、令牌或带签名的 CDN URL。已有字节数以实际文件状态核对，不能只相信状态文件。

已验证 blob 可以按 digest 复用，但解析和下载仍遵循本次明确选择的 Registry。缓存不能变成暗中切换仓库或跳过来源策略的理由。

恢复事务使用稳定键，由规范化 Registry 主机、仓库路径、blob digest 和预期大小派生；同一来源下跨调用可找到半包。凭据不参与键，也不落盘。鉴权仍使用当前调用配置。不同来源的半包不混用，完整且重新校验的相同 digest 内容可以复用。

已固定 digest 的计划可在有效缓存命中时不访问网络；这只证明本地内容满足计划，不证明 Registry 当前可达或当前凭据有效。需要解析可变 tag、版本索引或检查远端权限的操作仍必须执行自己的远端检查。

此目录是内部 content store，不能仅凭 `blobs/` 就称为完整 OCI Image Layout；离线导出格式不在本次设计范围。

## 5. 获取、恢复和提交过程

1. 解析组件、版本和平台，取得固定的 manifest digest 和所需内容清单。
2. 获取生命周期共享锁及提取快照锁，再检查有效的提取缓存。命中时复用；损坏时明确失效，重新构建。
3. 获取原始内容锁，锁内再次检查，避免多个进程重复下载。
4. 未命中时写入 ingest。若存在匹配的未完成数据，核对状态后请求剩余范围。
5. 完整下载后校验预期长度及 digest，成功后原子提交至 blobs。
6. 从本地已验证内容提取所需文件，流式写入暂存位置并校验文件摘要。
7. 在同一文件系统的暂存目录内完成所有文件和 receipt，同步文件后整体 rename 发布快照，再同步父目录。已有相同快照时锁内校验并复用，不覆盖正在使用的目录。完整记录可见前，安装步骤不得将其视为成功缓存。
8. 返回带释放操作的获取结果；调用方在复制、解包或 Helm 消费完成后释放使用保护。仅在 Fetch 内加锁、返回裸路径后立即解锁不能保证安全。

### 5.1 校验及提取契约

| 对象 | 校验依据 | 不可混淆的边界 |
| --- | --- | --- |
| 平台 OCI manifest | 计划固定的 manifest digest | index digest 与平台 manifest digest 分开处理 |
| 原始层 | 已验证 manifest 的 descriptor size 和 digest | 对 Registry 返回的原始压缩字节校验，续传偏移也基于这些字节 |
| 包内文件 | 包清单与计划一致的文件摘要 | 现有二进制按原字节计算；configs/charts 按 gzip 解压后的 payload 计算，不能直接改成归档文件摘要 |

blob 命中至少检查长度并流式重算摘要，再允许提取；receipt 命中同样验证本次所需文件。不能把文件名或历史提交成功当成本次磁盘内容完整的证据。缓存损坏时报告原因，释放本次已持有的全部锁及未返回的结果，再获取生命周期排他锁重新检查、删除损坏对象，释放后从流程起点重试一次。排他锁等待支持取消；不能从共享锁直接升级，也不能覆盖其他消费者正在使用的路径。再次损坏则返回错误，允许后续调用从指定来源重建；远端下载摘要错误则终止本次调用。

当前发布器把包清单和资产放在一个 rootfs 层中。首期按此包格式处理：原始层完整校验后，本地一次顺序扫描同时读取清单并暂存所需文件，最后统一校验再发布。清单位于文件之后也不能提前发布。重复目标路径、重复清单、缺失资产和不支持的层布局明确报错；不擅自实现通用容器 rootfs 的 overlay/whiteout 语义。

“join 只取 agent”指只提取、返回和分发 agent。若其与 server、kcctl 共处一层，仍需下载完整层；减少这部分网络字节需要另行修改发布布局，不属于本次修复。

只接受清单指定的普通文件，拒绝绝对路径、`..` 路径段、软硬链接及重复目标。暂存目录不含外部可写路径；文件、解压后 payload 和清单读取均需大小约束，超限失败。具体限制依据真实包大小确定，不把缺少解压后大小的旧清单当成零大小，也不宣称下载前空间估算能够杜绝 ENOSPC。

### 5.2 恢复状态与失败处理

“每层只完整下载一次”指同机、同 digest、缓存保留期间，正常获取完成后提取不同文件都读取本地内容。它不是一次 HTTP 请求的保证：断流、仓库忽略 Range、缓存被清理或换到另一台机器都可能导致额外传输。

恢复约束：

- 每层每次调用最多五次内容传输尝试，首次计入，指数退避加抖动，等待上限 30 秒；退避、锁等待及响应体读取支持 context 取消。鉴权和重定向不作为独立内容尝试，但有自身次数上限。禁止在业务层和传输层叠加不受控重试；退避基数 1 秒；所有内容重试共享上述五次预算。
- 重试从原 Registry blob 入口重新鉴权和跟随重定向，不复用过期签名地址。
- 206 必须匹配请求偏移、区间终点和预期总长度；错误范围明确失败。请求禁止透明 HTTP 内容解压，以免 Range 偏移与 digest 对象不一致。
- 本地长度等于预期长度时直接校验，不再发 Range；超过预期长度则废弃事务并报错。416 不视为成功，仅在本地长度等于预期且完整摘要通过时提交，否则失败。
- Range 被忽略而返回完整 200 时，明确从头写入，不能把完整响应追加在半包之后。
- 仅对明确可恢复的传输失败重试；永久鉴权错误、摘要不符、磁盘写入失败不包装成成功。
- 中断或取消可保留可恢复数据；长度或摘要错误的数据不得进入已验证区。
- 崩溃后重新检查 ingest；即使字节数已足够，也必须通过完整校验才能提交。

大文件采用流式处理，避免将整个安装文件读入内存。提取时限制目标路径，拒绝路径穿越和越界链接。不要为了提取 server、agent 而额外提取整个 bootstrap 包。

## 6. 并发、权限与清理

缓存目录延续私有目录权限，暂存内容仅对执行用户开放。原始内容完成后不可原地改写；提取文件按安装需要设置权限。

需要进程间锁，不能只使用 Go 进程内互斥。首期采用一个稳定的缓存生命周期读写锁，加每个提取快照锁和 blob 锁：

- 获取和消费持有生命周期共享锁，直到最后一个调用方释放结果；清理使用非阻塞排他锁，拿不到就跳过本轮清理。
- 获取按“生命周期 → 提取快照 → blob”的顺序持锁，每次只持一把 blob 锁。相同 digest 的下载串行，不同快照可以并行；不在持有共享锁时升级为清理排他锁。
- 锁等待采用可取消方式。锁文件放在独立 locks 目录，清理不删除、不重建锁文件。进程退出由操作系统释放锁；未完成事务留待下次恢复。

此方案会让长时间消费阻止整轮清理，但避免首期引入租约服务或引用计数数据库。容量压力下先在获取前尝试清理，仍不足则明确失败，不驱逐正在使用的缓存。以后只有实际观察到清理饥饿，才考虑细粒度保护。

多组件获取中途失败时释放已获取的所有保护；Release 必须可重复调用，消费错误不能绕过释放。安装时复制或解包到安装目录，禁止通过硬链接后 chmod、修改等方式改变缓存文件。

调用者需明确接管结果释放责任，包括 bootstrap 分发、Agent 解包和 Chart 消费。`ChartPath` 不能继续仅凭版本拼接新缓存路径，应使用获取结果提供的确切路径及保护句柄；卸载清理按组件身份枚举快照并在生命周期排他锁内删除。

清理策略：

- 提取文件是可重建结果；卸载只清理相应提取缓存，不删除共享 blob。
- 未完成数据使用单独保留期限，避免旧半包永久占空间。
- 完成内容受容量预算约束，优先回收长期未使用、当前无任务占用的内容。提取快照和 blob 独立回收，receipt 不构成永久保留 blob 的引用。
- 最近使用时间由成功消费后更新的轻量元数据记录，不依赖文件系统 atime；清理纳入 blob、提取快照和 ingest 的总占用。进程崩溃遗留的提取暂存目录也按未完成数据处理。
- 在获取或显式维护时执行清理，不增加常驻后台服务；容量预算不是运行中瞬时磁盘占用的硬上限。
- 下载前检查可用空间，考虑剩余压缩内容、所需提取文件和安全余量；空间不足时明确失败。
- 清理范围仅限缓存，不删除安装文件、containerd 镜像或目标 Registry 内容。

原始压缩内容和提取文件同时保留会增加磁盘占用。这是换取断点恢复和重复使用的成本。首期采用以下工程默认值，实施时用实际包体积验证，调整须同步本文与测试：

- 完整缓存安装后保留，不设置按时间自动过期；总容量软预算为 20 GiB。获取前及结果释放后尝试清理，超预算时按最近使用顺序回收到预算内；本次将使用的已知对象在获取前清理中排除。
- ingest 和提取暂存目录距最后写入超过 7 天才回收；未到期数据在容量压力下也可回收，但不得影响正在运行的任务。清理后再次获取允许重新下载，不承诺半包永久保留。
- 单次工作集超过预算仍允许执行，前提是可用磁盘满足需求；预算是保留目标而非包大小限制，任务释放后可能回收超额内容。磁盘空间预检保留至少 1 GiB 余量，实际写入失败仍必须返回错误。
- 首期不增加独立清理命令或 UI 参数，默认值集中定义以便测试。没有新操作时不主动唤醒清理，因此 7 天表示下次清理时的资格，不保证到点删除。
- 最近使用元数据存放在快照之外，不改变不可变 receipt；更新失败可报告维护告警，不改变已经完成的安装结果。新写入对象缺少访问记录时以提交时间作为回收排序依据。

## 7. 各条路径如何使用

| 路径 | 缓存所在位置 | 建议接入方式 |
| --- | --- | --- |
| kcctl deploy/join | 运行 kcctl 的机器 | 包获取使用统一存储；只提取本次部署资产，再分发到目标节点 |
| Agent 安装 containerd/Kubernetes 等 | 执行任务的节点 | 复用包获取实现；本机缓存与 kcctl 所在机器并不共享 |
| Registry 引导安装 | 执行命令的机器 | 核对现有独立下载路径，避免出现另一套不校验、不恢复的包获取实现 |
| Helm Chart | 实际执行 Chart 获取的机器 | 先区分包内 Chart 和原生 Helm OCI Chart，保留 Helm 语义，再评估底层传输复用 |
| registry sync | 执行 sync 的机器及目标 Registry | 复用完整性与恢复原则；保持 manifest/index、架构选择和目标校验语义，不默认永久缓存全部镜像 |
| 运行时容器镜像 | 目标节点 containerd 存储 | 交由 containerd 拉取和管理，不再完整复制一份到 KubeClipper 缓存 |
| 版本索引与元数据读取 | 索引执行方 | 保持轻量，不能为了列出版本下载所有完整层 |

统一的是获取与验证规则，不要求所有对象经过包提取器。尤其不能把 sync 的完整 OCI 图复制、Helm Chart 获取、运行时镜像拉取硬塞进二进制包接口。

## 8. 实现选型与分期

优先复用现有依赖。项目已有 containerd `v1.6.19` 和 go-containerregistry `v0.20.2`。

containerd 的独立本地 content store 可以在没有 containerd daemon 时使用，提供 ingest、Writer、长度和 digest 校验、完成内容提交等基础能力，作为首选，实施前做小范围契约验证。已核对锁定版本的 `NewStore`、`Writer`、`Status`、`Commit` 源码：可以复用其存储和提交能力，但根目录需由调用方以私有权限预先创建，跨进程协调由外层负责。它不自动解决我们的跨进程锁、缓存预算、权限要求和所有响应体中断；不能仅替换库就宣称问题已解决。

Registry 地址解析、认证、证书和重定向凭据边界继续复用现有能力，避免自行再实现一套认证协议。使用现有依赖的具体 API 前，需以项目锁定版本验证，而非套用最新版文档。

分两步，不把后续设想混入本次已完成范围：

1. **首期实现范围**：包获取的完整暂存、校验、本地提取、有限恢复和取消；deploy/join 资产筛选；缓存权限、并发与生命周期的必要处理。实现以本文为依据，同步关联变更规格；旧 Shape 中与本文冲突的部分不自动生效。
   Registry 引导安装首期仅核对是否调用同一包获取器；共用路径自然受益，独立路径不额外改造。完整图复制、原生 Chart 和运行时镜像不作为首期验收目标。
2. **后续获取路径收敛**：审计并分别决定 sync、Registry 引导安装、Chart 获取的接入方案。保留各自语义和独立验收，不宣称它们已由第一步自动覆盖。

不增加数据库、通用下载服务、共享文件系统或新的运行时依赖。不为未来假设预先构建复杂插件框架。

## 9. 验证计划与证据边界

- 冷缓存多文件获取：每个所需层只完整获取一次，核对网络字节和内容摘要；暖缓存不重复获取已有效缓存的包。
- HTTP/HTTP2 响应体中断：检查有限恢复、错误 Range、忽略 Range、重试耗尽、跨调用恢复和取消。
- 内容正确性：坏摘要、错误大小、损坏本地缓存、异常提取路径均明确失败，不出现完成记录。
- 文件系统行为：磁盘写入失败、权限不足、进程中断、并发下载、读取与清理竞争；验证锁不会失效或死锁。
- 来源安全：认证、HTTP/HTTPS、自定义 CA、证书校验、路径前缀和跨域重定向凭据隔离保持正确；日志不输出敏感信息。
- 资产选择：deploy 不提取或分发 kcctl，join 只提取和分发 agent；同层完整下载符合预期，缺失资产仍明确失败。
- 快照身份：不同请求顺序命中同一 selection；join 与 deploy 交替执行不覆盖对方目录。Fetch 返回后故意延迟消费并运行清理，确认文件仍可读取；释放后可清理。
- 校验语义：二进制原字节摘要和 configs/charts 解压 payload 摘要分别覆盖；禁止用测试中人为统一的摘要语义掩盖真实格式差异。
- 崩溃恢复：分别在下载结束未提交、文件写完未发布、快照发布后中断进程，验证只有完整且校验通过的快照可命中。
- 在 sh-dev 使用包含相关本地未提交和新增文件的独立源码快照，先核对文件清单和哈希，再运行构建与适当测试。
- 使用候选代码真实拉取 GHCR 物料，记录完整层与提取文件校验结果。清单读取成功、完整拉取、平台安装、建群成功分别报告，不相互替代。
- 使用只读独立验收检查全部已确认标准；不改动现有预览平台和用户集群来获得测试结果。

## 10. 定稿范围与实现检查点

本次定稿确定缓存位置、内容与快照身份、恢复规则、锁与消费保护、初始清理策略及首期路径范围。无需再为这些方向单独确认；本文不授权提交、部署，也不代表关联旧规格全部获批。

以下是实现必须完成的验证，不是悬而未决的架构选项：

1. 对锁定版本的 content store 做权限、续写、提交和崩溃恢复契约测试；验证现有认证 transport 能否提供正确的 Range 响应处理。若不能满足，明确报告差距并修订方案，不能以静默整包重下冒充续传。
2. 统计实际包体积并确定清单、文件和解压 payload 的读取上限；验证 20 GiB 预算和 1 GiB 空间余量在测试物料上的行为。限制必须在实现验收前明确并覆盖边界测试。
3. 完成 `ChartPath`、清理和所有包获取调用者的保护句柄接入，禁止遗留直接拼路径并读取的旁路。旧缓存失效重建，不增加长期兼容分支；旧目录在统一清理锁下回收。
4. Registry 引导安装仅验证是否共用包获取器；独立实现、sync 及原生 Helm OCI Chart 的改造留到后续，不计入首期已覆盖范围。
5. 增加纯本地重建验收：保留已验证 manifest 和层、删除提取快照、阻断网络，使用固定 digest 计划重新提取成功；完整缓存保留、容量回收和 7 天半包清理分别测试。

评审结论：按上述契约实施。文档检查仅证明设计内部一致性；第 9 节的代码、故障注入和真实物料验证通过后，才能宣称功能完成。
